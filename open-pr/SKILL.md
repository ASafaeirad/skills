# Open PR

A pull request is a request. Someone has to read it, form a judgement.
Everything below follows from writing for that person rather than for the log.

## Their git state is theirs

If the worktree is dirty and they did not mention committing, stop and ask what
belongs in this PR. Some of that mess may be deliberate, and some of it may be
someone else's. Never quietly stage, amend, rebase, or force-push to make the
tree convenient for you.

If a PR already exists for this branch, push to it and say so. Do not open a
second one.

## Write for the person who has to say yes

The diff already says what changed. The body is for what the diff cannot show:

- **Why this exists.** The problem, the bug, the request. A reviewer who does
  not know why cannot tell whether the approach is right.
- **The shape of the change,** where it is not obvious from the files, the one
  decision everything else follows from.
- **Where to look hard.** Name the risky part. Reviewers have limited attention
  and spend it on whatever you point at, so point at the thing you are least
  sure of rather than the thing you are proudest of.
- **What you deliberately left out,** and why. This pre-empts half the review
  comments.

Length follows the change. A one-line fix does not need headings. Do not pad a
small PR into a template, and do not compress a genuinely complicated one into a
sentence.

## Be honest about its state

Say what is untested, what is a stopgap, what you could not verify, what you
worked around. A reviewer who discovers an omission you knew about stops
trusting the rest of the description, and they were going to discover it.

This also means not claiming green when it is not: report what the tests
actually did, including failures you left in place.

## Size is a review problem, not a style preference

If the branch does several unrelated things, say so before opening it and offer
to split it. A reviewer can hold one change in their head and will approve it;
they cannot hold four and will skim. When the user wants it as one PR anyway,
open it as one and use the body to walk through it change by change.

When the work needs two or more small PRs, make a stack with `gh stack`. Do not
create the PRs one at a time with `gh pr create`. Order branches from the
foundation to the final dependent change. The bottom PR targets the trunk, and
each later PR targets the branch below it.

Write every PR so it can be reviewed on its own. State where it sits in the
stack and what must merge before it.

## Then take it green

Do not hand back a PR and walk away from a red build. Follow the checks with
`gh pr checks --watch`, read the log of anything that fails, and fix it. For a
stack, watch every PR, starting at the bottom. Keep going until they pass. A red
PR is not finished work, whatever caused the red.

Two things to hold onto while you do that. **Retrying is not fixing**: if you
suspect a flake, rerun it once to confirm, then find out why it is flaky rather
than rerunning until it blinks green. **Say what you touched**: when the cause
turned out to be unrelated to your change, the extra commits belong in the PR
body, called out as such, so the reviewer knows why the diff grew.

If a fix genuinely needs a decision you cannot make a dependency to bump, a test
whose intent is unclear, an infrastructure failure with no code fix stop and put
it to the user rather than guessing.

You are done when every PR is open, the checks are green, and the user has all
the links.

## Style

If you need to commit some changes please check the previous commits for style
and consistency.

Use markdown for formatting your PR description when it helps readability.

## Be explicit about the Author

Please add this note to the PR so the user can track who created the PR.

```
> [!NOTE]
> This PR is generated by <MODEL_NAME> using <HARNESS_NAME>.
```
